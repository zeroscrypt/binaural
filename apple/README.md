# apple/ — Swift implementation (macOS + iOS)

The second, independent implementation of Binaural: a native app written in Swift.
It is not a replacement for the Python code and not a line-by-line port of it — it is a
parallel product for Apple platforms that must behave the same way.

```
apple/
├── project.yml             # xcodegen: one project, five targets
├── build_release.sh        # Release .app into dist/, unsigned, self-verifying
├── DESIGN.md               # design notes — read this first
├── Binaural.xcodeproj      # generated by xcodegen, never committed
├── Sources/
│   ├── Core/               # platform-independent: no AppKit, no SwiftUI
│   ├── macOS/              # the AppKit app
│   └── iOS/                # SwiftUI app shell
├── Tools/                  # regenerates the Russian catalogue from src/
└── Tests/
    ├── CoreTests/          # parity tests against the Python reference
    └── MacTests/           # window tests (SPEC §7)
```

## Why a second implementation exists

| | `src/` (Python + Qt) | `apple/` (Swift) |
|---|---|---|
| Platforms | macOS, Linux (Windows next) | macOS, iOS |
| Build | PyInstaller | xcodegen + xcodebuild |
| Distribute | `curl \| sh` + tar.gz | unsigned `.app` from `./build_release.sh`; App Store needs an account |

One product per platform. The two share **data and behaviour**, never source code: a frequency
reference and a contract are portable, a Qt widget tree is not.

## Status

**M1 — foundation: done** (commits `a17cb62`, `1d17c9f`).

- `BinauralCore` is a single multiplatform framework (macOS + iOS) with five files —
  `BeatMath`, `StereoOscillator`, `Synthesizer`, `FrequencyCatalogue`, `Session`. No AppKit,
  no SwiftUI inside it, so the same code is testable on both platforms.
- Two app shells that build, launch and display that the catalogue actually loaded.
- `BinauralCoreTests` — **73 tests proving parity with Python**, not merely that the code
  compiles: 9 categories / 99 entries, evidence totals 68 🟣 / 12 🟢 / 11 🟡 / 8 🔵, per-category
  counts identical, `pair(10 Hz, 200 Hz) → 195 / 205`, synthesiser frequency within 1.0 Hz
  (and an exact closed-form check at 1e-6), peak amplitude within 1e-3, session save→load
  round-trip with Python's clamps.

**M2-a — done:** live audio output, i18n, the main window.

- **Live audio.** `AVAudioEngine` + `AVAudioSourceNode` feeding `StereoOscillator.render(frames:into:intoRight:)`,
  at the **device's own sample rate and channel layout** (this Mac's output is 44.1 kHz, and a
  test asserts the engine adopts what CoreAudio reports rather than a hardcoded 48000). Play, stop,
  frequency changes and mute all go through the accumulating fade from M1, so nothing clicks.
  Volume drives the oscillator's gain, not a scale of the buffers.
- **The thread handover** is the interesting part and is written up in [DESIGN.md §7.2](DESIGN.md):
  a `RenderParameters` value type crossing through one `NSLock` used with a **non-blocking
  `try`**. The audio thread never waits — a lost race costs one block of stale parameters, not a
  dropout — and the oscillator is created *on the audio thread*, so `StereoOscillator` stays
  non-`Sendable` exactly as M1 left it.
- **i18n, before the UI.** `L10n.tr` in `Core`, English as the source language (no table, so a
  missing key returns itself by construction), and `RussianCatalogue.swift` **generated** from
  `src/binaural/locales/ru.py` by `Tools/generate_russian_catalogue.py` — 171 keys, ru.py's order
  and section comments. Switchable live from *View → Language*, persisted under `ui/language`
  (Python's own key). `L10nKeysTests` scans the sources and fails if any string is untranslated.
- **The main window** per SPEC §7: two independent frequency controls (1–20000 Hz, 0.1 Hz step,
  exact keyboard entry), live `Beat` / `Carrier` with the §F1 out-of-range hint, Space to toggle,
  volume and mute, an always-visible headphone indicator, and a session restored on launch and
  saved on change (`~/Library/Application Support/app.binaural.mac/session.json`).
- **Tests: 169** — the 73 M1 parity tests unchanged, plus 75 core tests and 21 window tests.

**M2-b — the feature list is landed** — [DESIGN.md §9–§15](DESIGN.md) has one section per item.

- **Presets** (SPEC §5 F3): the two-level bar from §7, below the timer. Seven category
  chips, then the presets of the selected one; a category is state and goes into the
  session, a preset click sets **both** channels so the difference is the beat.
- **The timer** (§5 F5), **the headphone check at launch** (§4, heuristics then the
  perceptual L/R test), **Settings** and **About** (§7), the **menu-bar status item**
  (§7, Python's `TrayController`), and a **Release build** (§ "Release build" below).
- **Tests: 190 core + 114 window.** `PresetCatalogueTests` states F3's registry rules
  (20 presets, exactly one half-open band each, no Gamma); `PresetBarTests` drives the
  real window — chips in registry order, every preset setting `200 ± beat/2`, both
  languages, and the wrapping at 560 pt and 1400 pt.

Still open: running the suite on the iOS Simulator (no runtime installed), and the
perceptual-test edge cases that only a human with headphones can judge.

`WavWriter` is deliberately absent: the Python tree has no WAV writer either, and SPEC §F5
calls export optional (P2). Nothing is invented here to look complete.

## Build

```bash
cd apple
xcodegen generate

xcodebuild -project Binaural.xcodeproj -scheme BinauralCore \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build
xcodebuild -project Binaural.xcodeproj -scheme BinauralCore \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO test      # 148 core tests
xcodebuild -project Binaural.xcodeproj -scheme Binaural \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO test      # + 21 window tests
xcodebuild -project Binaural.xcodeproj -scheme Binaural \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build
xcodebuild -project Binaural.xcodeproj -scheme Binaural-iOS \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

Smoke test — a build that crashes on launch is not a passing build:

```bash
APP=$(find ~/Library/Developer/Xcode/DerivedData/Binaural-*/Build/Products/Debug \
      -maxdepth 1 -name 'Binaural.app' | head -1)
open "$APP" && sleep 4 && pgrep -fl 'Binaural.app/Contents/MacOS'
pkill -f 'Binaural.app/Contents/MacOS'
```

`CODE_SIGNING_ALLOWED=NO` is not optional here — see below.

## Release build

```bash
cd apple
./build_release.sh            # build apple/dist/Binaural.app
./build_release.sh --smoke    # …and launch it, confirm it stays alive, kill it
```

The script builds Release into a throwaway derived-data directory, copies the finished
bundle to **`apple/dist/Binaural.app`**, and deletes the build tree. So the app you keep
does not point into DerivedData: double-click it, or

```bash
open apple/dist/Binaural.app
```

No Xcode needed. **`frequencies.json` is verified, not assumed** — the script compares the
bundled copy against `src/binaural/data/frequencies.json` with `shasum` and `cmp`, and
fails if they differ, which is how CONTRACT rule 10 stays enforced at packaging time.

**It is unsigned.** `security find-identity` reports 0 identities on this machine, so the
build passes `CODE_SIGNING_ALLOWED=NO`; there is no fake signature and no notarisation.
The app runs for the person who built it. Handing it to anyone else means Gatekeeper
objecting and a right-click → Open, and distribution proper needs an Apple Developer
account — out of scope, not faked (M2.md §11).

`--smoke` also diffs `~/Library/Logs/DiagnosticReports` before and after, so a build that
launches and crashes a second later fails rather than passing.

## Prerequisites and signing

- **Xcode 27.0 (Swift 6.4)** and `xcodegen` (`brew install xcodegen`). `tuist` and `swiftgen`
  are not installed and are not used.
- **No Apple Developer identity is configured** — `security find-identity` returns nothing.
  Consequently every build passes `CODE_SIGNING_ALLOWED=NO`, and iOS can only be built for the
  **simulator**. Deploying to a physical iPhone requires a certificate: a free Apple ID signs
  for 7 days (re-signed from Xcode each week), the paid membership for a year.
- **This machine has no iOS Simulator runtime installed** (`xcrun simctl list runtimes` is
  empty), so the iOS scheme is compiled against `generic/platform=iOS Simulator` — that is a
  build-and-link check, not a run. `xcodebuild -downloadPlatform iOS` upgrades it to a real
  run-on-simulator check with no other change.
- `apple/Binaural.xcodeproj` is generated from `project.yml` and is gitignored; it carries
  machine-specific state and would conflict on every regenerate.

## One file, both implementations

`frequencies.json` lives once, at `src/binaural/data/frequencies.json`, and is read by both.

- **Python** reads it next to its own module, which is the only layout `pip install` carries
  into `site-packages`.
- **Swift** gets it through an xcodegen copy-files phase pointing at
  `$(SRCROOT)/../src/binaural/data/frequencies.json`; the tests rebuild the same path from
  `#filePath`, so a failing count always tracks the file currently being edited.

Do not duplicate it — the reference is edited constantly and two copies would drift.

## What happens to the Python macOS build

When the Swift macOS app reaches feature parity, the *release* packaging of the Python app for
macOS goes away: `scripts/build_macos.sh`, `packaging/macos/Info.plist`, and the `macos-arm64`
/ `macos-x64` branches of `install.sh`.

The Python code itself stays. You develop on a Mac, so `src/binaural/audio/platform/macos.py`
and running from source (`PYTHONPATH=src .venv/bin/python -m binaural.app`) keep working — the
ability to test the Python app locally is not something to give up.
