# apple/ — Swift implementation (macOS + iOS)

The second, independent implementation of Binaural: a native app written in Swift.
It is not a replacement for the Python code and not a line-by-line port of it — it is a
parallel product for Apple platforms that must behave the same way.

```
apple/
├── project.yml             # xcodegen: one project, four targets
├── DESIGN.md               # M1 design note — read this first
├── Binaural.xcodeproj      # generated by xcodegen, never committed
├── Sources/
│   ├── Core/               # platform-independent: no AppKit, no SwiftUI
│   ├── macOS/              # AppKit app shell
│   └── iOS/                # SwiftUI app shell
└── Tests/
    └── CoreTests/          # parity tests against the Python reference
```

## Why a second implementation exists

| | `src/` (Python + Qt) | `apple/` (Swift) |
|---|---|---|
| Platforms | macOS, Linux (Windows next) | macOS, iOS |
| Build | PyInstaller | xcodegen + xcodebuild |
| Distribute | `curl \| sh` + tar.gz | App Store / TestFlight, or a local `xcodebuild` archive |

One product per platform. The two share **data and behaviour**, never source code: a frequency
reference and a contract are portable, a Qt widget tree is not.

## Status

**M1 — foundation: done** (commits `a17cb62`, `1d17c9f`).

- `BinauralCore` is a single multiplatform framework (macOS + iOS) with five files —
  `BeatMath`, `StereoOscillator`, `Synthesizer`, `FrequencyCatalogue`, `Session`. No AppKit,
  no SwiftUI inside it, so the same code is testable on both platforms.
- Two app shells that build, launch and display that the catalogue actually loaded.
- `BinauralCoreTests` — **73 tests proving parity with Python**, not merely that the code
  compiles: 9 categories / 99 entries, evidence totals 68 🟣 / 12 🟢 / 11 🟡 / 8 🔵, per-category
  counts identical, `pair(10 Hz, 200 Hz) → 195 / 205`, synthesiser frequency within 1.0 Hz
  (and an exact closed-form check at 1e-6), peak amplitude within 1e-3, session save→load
  round-trip with Python's clamps.

**M2 — not started:** live audio output from an `AVAudioEngine` callback, headphone detection
and the perceptual L/R test, the real UI (two frequency controls, beat/carrier readout, preset
chips, reference browser, timer, volume, EN/RU switch), and running the test suite on the iOS
Simulator rather than just compiling for it.

`WavWriter` is deliberately absent: the Python tree has no WAV writer either, and SPEC §F5
calls export optional (P2). Nothing is invented here to look complete.

## Build

```bash
cd apple
xcodegen generate

xcodebuild -project Binaural.xcodeproj -scheme BinauralCore \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build
xcodebuild -project Binaural.xcodeproj -scheme BinauralCore \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO test
xcodebuild -project Binaural.xcodeproj -scheme Binaural-iOS \
  -destination 'generic/platform=iOS Simulator' CODE_SIGNING_ALLOWED=NO build
```

`CODE_SIGNING_ALLOWED=NO` is not optional here — see below.

## Prerequisites and signing

- **Xcode 27.0 (Swift 6.4)** and `xcodegen` (`brew install xcodegen`). `tuist` and `swiftgen`
  are not installed and are not used.
- **No Apple Developer identity is configured** — `security find-identity` returns nothing.
  Consequently every build passes `CODE_SIGNING_ALLOWED=NO`, and iOS can only be built for the
  **simulator**. Deploying to a physical iPhone requires a certificate: a free Apple ID signs
  for 7 days (re-signed from Xcode each week), the paid membership for a year.
- **This machine has no iOS Simulator runtime installed** (`xcrun simctl list runtimes` is
  empty), so the iOS scheme is compiled against `generic/platform=iOS Simulator` — that is a
  build-and-link check, not a run. `xcodebuild -downloadPlatform iOS` upgrades it to a real
  run-on-simulator check with no other change.
- `apple/Binaural.xcodeproj` is generated from `project.yml` and is gitignored; it carries
  machine-specific state and would conflict on every regenerate.

## One file, both implementations

`frequencies.json` lives once, at `src/binaural/data/frequencies.json`, and is read by both.

- **Python** reads it next to its own module, which is the only layout `pip install` carries
  into `site-packages`.
- **Swift** gets it through an xcodegen copy-files phase pointing at
  `$(SRCROOT)/../src/binaural/data/frequencies.json`; the tests rebuild the same path from
  `#filePath`, so a failing count always tracks the file currently being edited.

Do not duplicate it — the reference is edited constantly and two copies would drift.

## What happens to the Python macOS build

When the Swift macOS app reaches feature parity, the *release* packaging of the Python app for
macOS goes away: `scripts/build_macos.sh`, `packaging/macos/Info.plist`, and the `macos-arm64`
/ `macos-x64` branches of `install.sh`.

The Python code itself stays. You develop on a Mac, so `src/binaural/audio/platform/macos.py`
and running from source (`PYTHONPATH=src .venv/bin/python -m binaural.app`) keep working — the
ability to test the Python app locally is not something to give up.
